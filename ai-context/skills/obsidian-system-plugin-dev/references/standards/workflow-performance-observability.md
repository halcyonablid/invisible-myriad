# 工作流性能、测试点与扩展性

适用：未来新插件的设计、实现和验收；现有插件的跨 owner 工作流或性能敏感改动。简单纯 UI 修改只检查受影响的交互和工作量。本文规定开发方法，不表示当前插件已经具备这些测试点，不授权批量插桩或运行库部署。

## 1. 先确定一次操作的完整边界

为主要工作流写一张场景卡，说明用户触发、输入规模、正确结果、owner/provider/consumer、依赖版本、通知扇出及后台任务。新插件从设计阶段填写，实现阶段实际接入适用测试点，验收阶段提供启停和采集步骤。无跨插件或异步工作的简单插件可只接入口、可交互结果和关键工作计数。

把现有系统边界图与调用时序图标上观测点，不另画一套冲突的架构。典型协作见 [有效主键到下一步行动](<../../../../memory/obsidian-plugin-system/atlas/workflows/operational-context-to-next-action.md>)。分别定义：

| 终点 | 判定 | 不能替代它的信号 |
| --- | --- | --- |
| `commit_confirmed`（有写入时） | owner 确认提交，并有可核对的结果/receipt | 仅发出请求、已关闭弹窗 |
| `user_ready` | 指定正确结果已显示，约定的下一次交互可执行 | 骨架屏、旧缓存预览、spinner 消失、Promise 返回或单次 rAF |
| `related_work_settled` | 本次操作引起的相关队列/重建达到场景规定的结束条件 | 所有插件完全空闲、只看当前页面 |

`user_ready` 的验证应同时核对显示结果身份/新鲜度与一次无破坏性的交互，不能靠占位提前结束计时。若允许先看旧结果，另记 `preview_ready`，不要把它混入最新结果的耗时。后台观察使用有界窗口，超出窗口记 `unfinished/censored`，不是零成本；区分观察截止、业务超时与实际任务完成。

## 2. 新插件的观测契约

先发现可复用的现有诊断能力，再选择局部 collector 或兼容的只读诊断接口，不强制建立全局遥测服务。例如 Atlas 已记录 PEO 的 `window.__PEO_PERF_DIAG === true` 开关，但是否提供完整跨插件关联要重新查代码，不能凭开关名推断。

关键点按实际链路选择：

| 边界 | 记录内容 |
| --- | --- |
| 用户动作入口/结果就绪 | 场景、触发方式、结果判定、成功/失败 |
| provider 请求/排队/返回 | provider、请求范围、队列等待、结果规模、错误与代际 |
| owner 提交/回执 | 请求是否被接受、提交是否已确认、幂等命中；不存正文 |
| 通知发出/接收 | 起因、接收者数量、合并/丢弃及原因 |
| 失效/重建/渲染 | 实际执行次数、失效理由、过期结果是否拒绝 |
| 后台结束/窗口截止 | 相关待处理数、结束原因、未完成任务数 |

每个异步 span 都有结束或明确未完成状态，异常/关闭也能定位。时间使用同一时钟域的单调钟，附 `clockScope/sessionId`；跨进程不能直接相减单调时钟。elapsed 是等待时长，不是 CPU 使用量；嵌套或并行 span 不可累加冒充总耗时。

以下是未来实现时可选的设计形状，不是现有运行 API：

```text
schemaVersion, scenarioId, traceId, spanId, parentSpanId,
pluginId, pluginVersion, clockScope, sessionId,
phase, startMono, durationMs, outcome, reasonCode,
causedBy[], counters{}, droppedEvents
```

- `traceId` 关联一次用户操作；`spanId` 关联一次实际执行；多调用者共享任务用 `causedBy`/links 关联，不能给每个等待者重复记一份实际工作。
- 业务 `txId`、幂等 `requestId`、稳定 node key 保持原语义；trace 不是身份、写授权或 CAS 凭证。需要关联时保留本地映射或兼容字段。
- 跨插件只通过经契约核查的可选参数/接口传递观测上下文；旧版本不支持时降级为局部观测，记录关联缺口，业务仍可运行。不得偷偷把字段塞进业务 JSON 或修改签名。
- 可导出的诊断 schema 需有版本、能力探测、未知字段兼容、数量/字节限制、卸载清理和错误隔离；新增消费者不应要求读取 provider 私有 JSON。

### 开销与内容边界

详细性能 tracing 默认关闭或由明确、有界的诊断会话开启；在根操作决定采样并传播。使用有条数和字节上限的内存缓冲区，记录丢弃数与截断，设置诊断截止；停止/卸载时释放监听器、计时器和观察器。不得为了观测新增持续全库扫描或轮询。

热路径不要等待诊断写盘或序列化大对象；诊断异常不阻断提交。停用时应接近 no-op，按相同场景比较开/关的时间、事件量、内存和写盘额外成本，预算由基线与目标确定，不照搬统一毫秒阈值。

**这些开关与采样只适用于性能诊断，不能关闭已有必须的 tx/verify/summary/error 日志或业务审计。**继续遵守 [console 标准](console-logging-standard.md) 和 [审计协议](audit-trail-protocol.md)。本地必需的 notePath 不等于可以进入性能导出；导出不含正文、标题、绝对路径或业务 payload，使用诊断会话内可关联的 opaque 标识，hash 也不等于匿名。

用户显式触发诊断摘要导出/复制，检查脱敏和缓冲截断后用于反馈，不自动外发。若后续需要持久诊断文件，单独设计 owner、存储位置、保留/清理策略及适用的 Registry 分类；本规范没有部署此类存储。

## 3. 超时、缓存和并发的验证

- 等待超时不代表底层任务已取消。分别记录 timeout、abort requested、abort acknowledged、late completion；没有取消契约时，状态是仍运行或未知。
- 写入结果未知时先查 owner 的回执/幂等状态，不能盲目重做。提交已确认而投影刷新失败，应清楚显示已保存/待刷新，不能把刷新重试变成创建重试。保留原有草稿和关闭保护。
- 重试有截止、次数与退避上限；验证超时后后台工作是否累积。取消一个等待者不能未经约定取消其他等待者共享的任务。
- 相同请求合并需包含准确 source、scope/domain、revision/generation 和查询条件；缓存命中还要计入核验、失效、序列化及保留成本。旧资格快照不得授权写入，旧代任务不能覆盖新状态。
- 按影响面测试 provider 缺失/慢响应、并发修改、重复事件、失效风暴、缓存损坏、多个 host/source、关闭/卸载后的晚到结果。仅减少当前函数耗时不能放行后台退化。

## 4. 可重复的评估方法

### 建立基线

记录版本/hash、**磁盘已部署版本与进程实际加载版本**、宿主版本/设备、启用插件、打开页面、预热设置、数据/图规模和诊断开关。无法证明实际加载版本时标 unknown；磁盘 hash 不能替代宿主证据。

按实际使用选冷启动、暖会话、重启持久缓存、多页面/预热并行等场景，不把不同缓存状态或预热策略混入版本收益。不要为获得漂亮数字自动关闭用户认可的预热。

| 维度 | 观测内容 |
| --- | --- |
| 用户等待 | 点击到正确结果可交互；保存确认与投影完成分开；失败/超时率 |
| 工作量 | provider 请求与实际重建次数、事件接收/合并/丢弃数、读写次数/字节、缓存命中及核验成本 |
| 后台代价 | 等长观察窗口中的工作量、队列是否收敛、long task/事件循环延迟（支持时）、内存保留增长 |
| 扩展性 | 小/日常/增长规模；无关笔记增多是否拖慢局部操作，消费者增加是否倍增重建 |

按影响面补无操作 idle 基线、重复导航/创建后关闭循环，检查监听器、计时器、队列和内存是否累积。CPU/heap 不可测就写 unavailable，不用 elapsed 或单次 heap 读数冒充 CPU/泄漏结论。

### 前后对照和回归上限

同一场景前后配对，尽量交替 A/B 或平衡顺序；固定输入、缓存状态和背景工作，保留顺序、原始样本、失败和异常，不剔除慢样本来制造收益。涉及写入使用隔离夹具/专用测试库，不在真实库自动创建多条正式待办；真实业务操作需用户执行或明确授权。

少量样本报告每次、范围和中位数，不能把少量试跑的 p95 当稳定结论。分位数要注明样本量、超时/截断处理及不确定性；多个阶段并行时不要声称每项节省时间可直接相加。

可以把已证明与真实等待相关的稳定工作计数固化为回归上限；它只是一项哨兵，不能替代正确性、端到端与后台验收。耗时门槛依据重复观测与噪声容差，不因单次较快自动收紧，不因单次略慢自动回滚。数据规模、算法、功能契约变化后重新评估基线，记录调整原因，禁止静默放宽。给目标和停止条件，不追求无期限下降或为了几毫秒引入难维护的复杂度。

### 判定与交付

先写假设、收益目标、允许的代价与回退点，再做边界明确的改动。输出“保留/回退/继续观察”的证据；不能以降低新鲜度、缺失数据、跳过审计或放宽资格换性能。只做了静态/夹具测试，就写“功能/局部工作量已验证，真实宿主整体收益待验证”。遵守 [发布门禁](release-guardrails.md)，不新增独立授权或自动部署通道。

## 5. 反馈与长期知识

最小记录模板（按适用性填写，不可测注明原因）：

```yaml
scenario: 用户动作、正确结果、输入与数据规模
scope: owner/provider/consumer、依赖契约与影响面
environment: 磁盘版本/hash、实际加载版本、设备、页面、预热和缓存状态
endpoints: commit_confirmed / preview_ready / user_ready / related_work_settled
instrumentation: 已接入点、schema、如何启停、如何导出、开关额外成本、采样/丢弃
comparison: 前后原始样本位置、顺序、样本量、失败/截断和噪声
work_and_background: 计数、idle/负载窗口、收敛或unfinished、扩展规模
correctness: 身份、新鲜度、草稿、重复写入、退出和兼容性
verdict: 收益证据、代价、未测项、下一次采集触发与回退点
```

新插件交付必须给出真实实现中的测试点位置及最小反馈步骤：如何开始一次诊断 → 执行哪个场景 → 如何结束/取得有界摘要 → 反馈需附哪些版本/状态。没有原生运行证据时可先以隔离集成测试验证接入有效，明确真实运行待采集。

沿用 [Framework 更新协议](<../../../../memory/obsidian-plugin-system/framework/update-protocol.md>)：用户观察、代码事实、模拟集成、真实宿主测量、上线后重复反馈分开记录；用户说快了是实践证据，不是量化提速。原始样本/一次故障进入工程证据，稳定协作事实进入 Atlas，复用方法和长期问题进入 Framework；未证明的性能退化原因保留 unknown。经验按既有 MemPalace 流程处理，区分落盘、入库、可召回，不把 raw trace 或私有业务内容自动入库。

## 6. 外部方法的适配

方法参考：[Anthropic 工程文章](https://claude.dev/blog/how-we-made-claude-ai-faster/) 的完整用户流程与上线后验证；[huashu-flash](https://github.com/alchaincyf/huashu-flash) 的就绪定义、配对测量和回归上限。2026-10-01 阅读其 SKILL、measurement-protocol 和 ratchet.py，仅借鉴方法，未安装或运行外部脚本；外部数字不证明本系统收益。

本系统不照搬网站的 Fast 4G/SEO 指标、默认提速一半、固定十次就报告可靠尾分位、对噪声数值自动收紧或无期限优化。以宿主实际工作流、可靠样本、版本证据与后台成本决定适用方法；诊断代码自身也必须接受成本检查。
