# Audit Trail Protocol

## 1. 目标

审计留痕插件的职责是：

1. 接收业务插件发来的审计事件
2. 编号
3. 落盘
4. 查询 / 导出

它不是：

1. DOM 扫描器
2. 事后猜 diff 的解释器
3. 代替业务插件保存内容的组件

## 2. 正交原则

### 业务与监管分离

业务插件负责：

1. 在正确时机发事件
2. 把对象、动作、前后差异说清

审计插件负责：

1. 写记录
2. 保证记录存在
3. 提供查询导出

### 人话优先

正式主记录不能暴露函数名、类名、局部变量名。

## 3. 两阶段模型

### `beginOperation`

记录“准备执行什么”。

### `finishOperation`

记录“执行完成还是失败，结果如何”。

### `recordOperation`

兼容旧路径或低风险单步操作的简化入口。

## 4. 主记录结构

正式主记录保持扁平字典，不要嵌套大对象。

核心字段至少应能表达：

1. `协议版本`
2. `序号`
3. `插件名`
4. `对象类型`
5. `对象名称`
6. `动作`
7. `结果`
8. `原文`
9. `修改后`
10. `发生时间`
11. `人工记录`

`人工记录` 应长得像人工工作日志，而不是程序调试输出。

## 5. 扩展字段协议

未来接新插件时：

1. 核心字段不变
2. 扩展字段统一用 `扩展_插件名_字段名`
3. 只保留能帮助人工追查的定位信息

## 6. 协议版本化与兼容

1. 主记录必须带 `协议版本`
2. 新插件接入时，优先新增扩展字段，不轻易改核心字段语义
3. 如果必须升级协议版本，旧版本记录仍应可读、可导出、可追查
4. 版本升级不能让历史记录“只剩机器能看懂”

## 7. 落盘格式

建议至少区分两层：

1. 机器主日志：完整 NDJSON / 等价机器可读格式
2. 用户导出日志：面向人读的 Markdown / 等价格式

如果用户导出或界面显示出于可读性做截断，机器主日志仍应保留全文。

## 8. 与 State Capsules 的边界

1. 留痕负责记录，不负责恢复业务状态
2. `state-capsules` 负责环境态，不负责接管业务审计
3. 两者可以协作，但不能互相篡位

## 9. 建议首批覆盖动作

至少覆盖：

1. Tab 增删改名
2. 条目增删改名
3. 评论修改
4. 绑定 / 解绑
5. 移动
6. 范式相关增删改
7. collection-card-view 的对应业务动作

## 10. 禁止事项

1. 让审计插件扫描 DOM 猜修改
2. 把业务插件内部函数名写进主记录
3. 截断机器主日志中的原文 / 修改后正文
