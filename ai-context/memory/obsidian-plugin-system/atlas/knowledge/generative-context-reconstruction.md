# Generative Context Reconstruction And Artifact-Centered Work

status: confirmed_by_user
created: 2026-07-21
layer: cognitive_hardware / execution / project_coaching

## Core Claim

For the user's current practice, re-entering a task works better when the user first reconstructs the current problem actively on blank paper, chooses the current work heuristically, and names a target artifact before consulting system history.

The system should then hydrate history in response to questions generated by the current artifact. It should not default to filling working memory with a complete historical account before the user has formed the current task model.

This is a confirmed user-practice claim, not a universal cognitive-science law.

## Two Cognitive Objects

The system contains two different objects that should not be conflated:

```text
long-term external cognitive hardware
  = Atlas, Framework, notes, Project Overview, Workspace, Keyword, history

current working-memory object
  = the PPT page, report section, model, decision, code or drawing being changed now
```

External cognitive hardware preserves memory, evidence and retrieval paths across time. The current artifact organizes attention and reasoning inside the present work session. Durable knowledge does not automatically deserve to occupy current working memory.

## Entry Modes

### Artifact Production / Continuation

Use when the goal is to continue making or changing a real object.

```text
active reconstruction
  -> current artifact
  -> current questions
  -> bounded historical retrieval
  -> immediate artifact change
  -> minimal handoff
```

The system opens only after the user can state:

- the current artifact;
- the next concrete edit;
- the historical question being asked;
- the artifact slot the answer will change;
- the retrieval stop condition.

### Evidence Audit / Diagnosis

Use when the task itself is to understand project state, compare sources, locate contradictions or prepare a coaching diagnosis.

Project Overview AI context export and a source-separated evidence ledger may be the first entry here. The evidence packet remains bounded, preserves ownership and recency, and eventually produces a diagnosis, decision, plan or other target artifact.

## Query-Driven Historical Hydration

History should be invoked by the current problem:

```text
current artifact asks a question
  -> Context Capsule Key identifies the operating context
  -> Project Overview / Workspace / Keyword / EVA locate bounded evidence
  -> relevant evidence returns
  -> artifact changes
```

This mirrors the system's summary-first and visible/current-first MapReduce prior: identity and compact state load first; detail hydrates only when it changes the current reduce result.

## Meta-Work Failure Mode

System activity can resemble progress while the target object remains unchanged:

- adding more entries;
- reorganizing categories;
- mounting more material;
- expanding intermediate notes;
- redesigning the work system during the work session;
- reading historical context without a current question.

These actions are not always waste. They become meta-work when they do not change the next decision, preserve unique evidence, reduce future resume cost, or create reusable knowledge.

## Minimal Handoff Contract

The end-of-session handoff should preserve only the state needed to restart active reconstruction:

1. target artifact and current location;
2. last substantive change;
3. next concrete edit;
4. blocker or unanswered question;
5. necessary historical pointers.

The handoff is not a full historical summary and not a list of every intermediate artifact.

## System Role Map

| Surface | Role in artifact-centered work |
| --- | --- |
| Blank paper | Active reconstruction and heuristic choice |
| Current artifact | Present working-memory center |
| Mandala | Posture/formula selection before execution |
| Project Overview | Evidence audit and bounded project diagnosis |
| Workspace Mount | Material rack and execution environment |
| Keyword | Question-driven entrance into historical material |
| GTD / Collection Card | Parking and explicit next-action support |
| Timeline | Time/resource reality check |
| EVA | On-demand relation traversal |
| Context Capsule Key | Stable operation identity for bounded recall |

## Guardrails

- Do not interpret this page as anti-history or anti-system.
- Do not force blank-paper reconstruction when the explicit task is evidence audit.
- Do not use a full evidence packet as the default task-initiation surface.
- Do not preserve every transient thought as durable system content.
- Do not discard intermediate artifacts that preserve unique evidence or materially lower future restart cost.
- Do not promote this user-practice claim to a universal rule without broader evidence.
