This page is the cross-plugin API map for the Obsidian plugin system.

It answers:

- which API exists;
- which plugin provides it;
- which plugin or workflow consumes it;
- whether it is read-only, owner-write, jump/reveal, adapter, or internal pipeline;
- what data boundary it must respect.

This page is not a second `contracts.md`.

- `contracts.md` owns rules, boundaries, ownership, and forbidden behavior.
- `api-registry.md` owns API inventory, calling direction, status, evidence, and operational use.
- `plugins/*.md` own per-plugin role maps and local guardrails.
- `framework/registry.md` only lists durable entrances.

## Ownership Rule

status: confirmed_by_memory

Ownership means: the plugin that owns a data domain is the only plugin allowed to write that domain directly.

Other plugins may:

- read owner-provided snapshots;
- ask the owner to create, update, reveal, or synchronize something through a narrow API;
- store their own derived display state or comments inside their own data domain.

Other plugins must not:

- directly edit another plugin's business JSON;
- repair or normalize another plugin's data during render, export, restore, or fallback;
- infer that a node key or visual relation grants write permission.

Practical meaning: Project Overview can aggregate Workspace, GTD, Mandala, Collection Card, EVA, and Keyword evidence, but it does not become the owner of their business JSON. If it needs Workspace data, it calls Workspace Mount APIs. If it needs a relation, it asks EVA. If Mandala needs Project Overview comment/meta, Mandala calls Project Overview's narrow owner API.

## API Types

| Type | Meaning | Write Boundary |
| --- | --- | --- |
| `read-only` | Returns identity, snapshot, evidence, or state without mutation. | Must not write business JSON. |
| `snapshot-family` | A read-only owner API pattern for summary-first, detail-on-demand provider snapshots. | Must call owner APIs only; must not force unrelated providers into the same method name or business shape. |
| `owner-write` | Lets the owner plugin create or update its own data. | May write only the provider's owned domain. |
| `narrow-write` | Lets a consumer ask a provider to write one scoped provider-owned field. | May write only the named provider-owned projection/comment/meta. |
| `embedded-view` | Lets one plugin host another plugin-owned view surface through a narrow render API. | The provider owns rendering, interactions, and any provider-domain writes; the host passes UI options and a container only. |
| `jump` | Opens or reveals a known node. | Should not mutate business data. |
| `adapter` | Registers provider items and openers for cross-plugin relation workflows. | Adapter registration may update adapter registry, not source business records. |
| `internal-pipeline` | Implementation scaffold inside one plugin. | Not a public cross-plugin API. |

`snapshot-family` is a registry classification, not proof of one universal API. A concrete row remains `confirmed_by_code` only when the method and return shape were checked in code or runtime output.

## Use Rules

Before adding, changing, or consuming an API:

1. Check this registry for the provider, consumers, type, and boundary.
2. Check `contracts.md` for the ownership rule and forbidden behavior.
3. Check the provider plugin page for local guardrails.
4. If a new consumer or changed shape is introduced, update this page and the relevant contract/plugin page.
5. Mark the claim status honestly; do not write `confirmed_by_code` unless code, runtime output, generated graph, or public API was checked.
6. For `snapshot-family` APIs, keep core envelope fields separate from subtype fields. Do not require Mandala, Keyword, or other domain owners to implement `getContextCapsuleCarrierSnapshot()` unless the Context Capsule carrier subtype is actually their domain.
7. Treat `cursor`, `nextCursor`, and `revision` as opaque provider-owned values unless a separate versioned pagination contract exists.
8. Before promoting a candidate snapshot-family API into Public Cross-Plugin APIs, record the provider owner boundary, summary/detail split, supported request keys, empty-match behavior, cache/invalidation rule, and at least one runtime/code evidence source.
