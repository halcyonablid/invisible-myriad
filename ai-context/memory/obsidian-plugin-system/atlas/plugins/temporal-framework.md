## Role

Temporal Framework is the strategic time-architecture owner. It turns existing managed goal/project identities into a top-down future plan across year, quarter, month and week without becoming another Mandala table or another Timeline item system.

## Owned State

- framework lifecycle and date boundary events;
- membership admission/exit events for imported stable primary identities;
- user-defined framework items and dated framework milestones;
- append-only framework-milestone bindings to one goal, project or outcome node;
- strategic outcomes and outline parentage;
- typed outcome relations;
- outcome Placement and declared home TimeBox scale;
- stage-gate policies;
- explicit no-deployment coverage decisions;
- manual completion paint/unpaint events.
- manual Outcome effectiveness boolean events (`effect-set`), independent of completion and scheduling.

The business file is `Temporal_Framework.json`. Load/read does not create it. First explicit owner mutation creates it through candidate, journal, previous-file and readback verification.

## Consumed State

For new membership admission, Temporal Framework calls both Mandala final read-only APIs: `listEffectiveOperationalContextKeys()` for projects and `listEffectiveGoalOperationalContextKeys()` for goals. It validates both frozen v1 envelopes and every target, including generated revision evidence, matching domain, complete Workspace/Mandala `jump:v1` identity, Context Capsule descriptor and unique `domain + scope + sourceKey`. One malformed/duplicate target or either incomplete domain rejects the whole candidate set; Temporal never silently filters it into a smaller success. It stores only the stable identity tuple and label snapshot needed for its own membership and never reconstructs eligibility from retained Mandala rows or Timeline history.

This rule is admission-only: an existing Temporal membership and its strategic outcomes/history are preserved when the source key later becomes inactive, stopped, killed, archived or carrier-missing. Historical `listTimelinePlanningTargets()` data remains a separate Timeline/planning compatibility path and no longer authorizes a new Temporal project membership.

When an outcome opens its owning goal/project Ontology, Temporal calls Mandala's additive `resolvePlanningTargetOntologyOwner()` capability and then forwards the provider-native `stableRef` to `openOntology()`. Temporal does not derive Workspace aliases or persist an Ontology address copy.

## Projection Model

Time, framework meaning and Outcome execution structure are orthogonal:

- Time-first: TimeBox outside, outcome cards inside.
- In the structured global Time projection, each TimeBox contains framework items, then goal/project membership roots and their local recursive execution forests. Milestones annotate directly bound nodes; they never become grouping containers that split the execution tree.
- Within each TimeBox, framework items are ordered by their earliest active milestone date. Items with milestones precede items without milestones; equal dates fall back to the earliest visible Placement, then item title and stable ID. The unassigned group remains last.
- Within a framework item, goal/project membership roots are ordered by the lexicographic date sequence of active milestones directly bound either to that membership or to its active outcomes. Shared milestone IDs are deduplicated, a shorter common-prefix sequence comes first, and memberships without milestones remain in a deterministic tail. Invalid historical bindings fail closed and never rewrite owner state.
- The Outcome overview reuses the same membership-root milestone ordering inside each framework item, while preserving the existing framework-item section and TOC order. This is a read-only projection contract; it does not change milestone ownership, direct-only semantics, events or Store history.
- Outcome-first: managed object/outcome outside, calendar facts and child outcomes inside.
- Effectiveness-first: only active Outcomes manually confirmed as `effective: true` are projected as framework item/unassigned -> owning membership -> one merged local outcome tree. A direct milestone is a property of its own outcome node, never a grouping key or inherited value. Parent and child selections in the same membership/framework-item context therefore remain in one tree even when their direct milestones differ or one side is unbound.
- Time breadcrumb and Outcome breadcrumb are independent.
- TimeBox is a derived `[startDate, endDateExclusive)` interval.
- Outcome outline, typed relations and Placement remain separate structures.
- Framework items have no software-defined type. A user names them directly and may leave a goal/project unassigned.
- A goal/project belongs to at most one framework item and may additionally bind to one active milestone under that item.
- An outcome remains owned by exactly one membership and one execution outline. It has a milestone only when that outcome has its own active direct binding. Parent outcomes, membership-level milestone bindings and framework-item assignment never supply an inherited outcome milestone.
- Cross-membership or cross-framework-item parentage remains readable through an explicit external-parent jump. The foreign ancestor is not copied as a complete local node, so one outcome tree does not silently duplicate across ownership/location boundaries.
- A parent outcome Placement defines the rail used to schedule immediate child intervals. New child intervals must remain inside the parent; historical overflow stays readable and receives an explicit repair action.
- In an Outcome-focused Time view, selection begins only from outcomes whose own valid active Placement intersects the TimeBox, then admits active same-membership ancestors as read-only context. An ancestor without its own overlapping Placement provides lineage only; it does not become selected, add to the TimeBox count or pull in siblings.
- Outcome focus preserves vertical TimeBox chronology while projecting each membership-local outcome tree as horizontal recursive containment: roots are outer containers, siblings share a responsive row, and deeper descendants repeat the same structure. Wide trees may scroll horizontally inside the bounded membership-local viewport, while tree width is prevented from escaping to the page.

## Scheduling Admission

Hierarchy and relation timing are enforced only when a relevant Placement or relation is newly created or changed. They are not global projection errors, so historical conflicts remain readable and diagnosable.

- `precedes`: source `endDateExclusive <= target.startDate`;
- `requires`: source effective due date is earlier than target `startDate`;
- `contributes_to`: contributor effective due date is no later than the gate effective due date;
- effective due date is `dueOn`, falling back to the last included interval day.

Placement drag, keyboard adjustment and exact-date forms share the same admission function. Drag release uses the revision captured at interaction start; cancellation paths do not write.

## Framework Boundary Revision

An active framework can revise its start and exclusive end boundary through one append-only `framework/revise` event. The operation never moves, trims, deletes or migrates Placements, Coverage, outcomes, completion history, relations or membership planning snapshots.

Every active Placement in the framework must remain fully contained, including anomalous active Placements whose outcome has been archived. Active `no_deployment` Coverage may partially intersect the new framework, but may not be fully excluded; its complete canonical TimeBox identity and policy version must still match. Unscheduled outcomes, relations, completion history and membership planning snapshots do not independently block revision. No-op, stale-revision and failed admission append no event and preserve persisted Store bytes.

Both an existing active-relation conflict and a timing conflict discovered while creating a new relation can open a joint adjustment transaction. The editor starts from the two relation endpoints, then follows only currently violated active relation and parent-child containment edges. Every adjustable outcome discovered by that violated-edge closure receives another track; newly exposed conflicts extend the closure recursively after an interaction. Unrelated historical conflicts are excluded, while a track already shown remains visible with a resolved cue when its conflict clears. A directly connected child without Placement, relation endpoint without Placement, or inactive/missing relation endpoint remains an explicit named non-adjustable blocker. Single-Placement admission omits only these unavailable-neighbor blockers so a parent or first relation endpoint can still receive its initial schedule; ordinary constraints between existing Placements remain enforced.

All displayed candidate Placements are projected simultaneously for admission, but persistence is based on semantic change rather than display membership. An unchanged track, including one moved and restored before save, emits no Placement event. Existing-relation repair appends `0..N` changed Placement events; new-relation adjustment validates candidate structure first and then appends one relation event plus `0..N` changed Placement events. Every event in one save shares a commit revision and consecutive ordinals through one `TemporalStore.save(expectedRevision)` call. Event identities are preflighted across all event buckets before the first append. Stale revision, malformed identity, missing Placement, duplicate event identity, any unresolved constraint or final Store rejection persists no partial event.

## Outcome Retirement

“放弃本次修改” discards only the current unsaved modal draft. “停用阶段成果” appends an outcome archive event and, when needed, a Placement unassign event. It never deletes historical events or recursively retires children. Active children of an archived parent remain visible as warned local roots.

## Membership Lifecycle

Temporal owns whether a Mandala goal/project identity participates in a framework. “移出时间框架” appends a membership exit event; it never deletes or edits the Mandala goal/project. Conservative admission allows exit only when the membership has never formed any outcome, including archived outcomes, and has no active no-deployment coverage. A reason is required.

Membership identity is unique for its entire lifetime within one framework. Reimporting an exited target reinstates the same membership ID instead of admitting a duplicate. Reinstate may refresh only `lastKnownLabel`, `sourceState`, `planningStart` and `planningEndDateExclusive`; `frameworkId`, `primaryRef` and `labelAtCreation` remain immutable. Exited memberships cannot create outcomes or no-deployment coverage.

## Framework Meaning Lifecycle

Framework-item and Outcome-effectiveness capabilities upgrade the owner Store from schema v1 to v2 only inside the first explicit new-capability transaction. Merely loading or reading v1 does not migrate or rewrite it. A v1 Store cannot contain v2 events, and a v1-only reader must reject v2 rather than silently preserve an incomplete projection.

Framework items, milestones and bindings use append-only lifecycle events. One active target has at most one active milestone binding, while one milestone may bind many different targets. Unbinding retains historical identity; an outcome then has no milestone unless it has another later direct binding. Active bindings block membership reassignment, unassignment and exit until explicitly removed. Archived bindings remain readable; active bindings require valid same-framework endpoints.

An active framework milestone must remain inside the framework date boundary. Boundary revision never moves or deletes milestones and is rejected when an active milestone would fall outside the candidate boundary.

## Completion Semantics

Completion is always a manual paint event. Gate readiness, elapsed dates, Timeline milestones and dependency completion cannot paint an outcome. Past incomplete outcomes remain unpainted with an overdue cue, including a non-color mark.

Outcome effectiveness is a separate manual boolean. Entering or exiting requires explicit confirmation and appends only the common event envelope plus `{ outcomeId, effective }`; there is no start date, expected date, note or reason. Same-value requests fail before schema upgrade or event append. The flag never blocks archive, reparenting, framework-item assignment or milestone bind/unbind. Archived Outcomes are hidden from the active projection while retaining their latest flag; restoration reveals it again.

Framework milestone progress is a read-only date projection displayed only inside the existing milestone card. Its start authority is `milestone-create.createdAt` interpreted in the Store timezone, and its end is the current `targetDate`. Upcoming, active, due, overdue, establishment-after-target and unavailable states are explicit; reaching 100% never completes or paints anything.
