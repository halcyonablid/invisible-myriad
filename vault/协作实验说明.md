# 大千协作内核实验 R0

大千基本版保留。这个实验副本把“协调顺序、阶段测量、重复通知刷新”抽成一个内核，各插件继续维护自己的界面和数据。它是以后模块合并的第一步，目前仍依赖原插件，不是已经完成的大插件。

## 能回答什么

统一协调有机会减少重复工作，但把文件装成一个插件本身不会自动提速。当前很多调用已在同一宿主里通过函数与事件协作；读取、等待页面加载、重复构建、刷新及后台竞争仍会存在。

源码证据：Mandala 新建项目/目标后，依次建立 Workspace、Collection、GTD 承载；这些接口可能打开页面再等待宿主。PEO 已有按域/用途合并在途构建，行动台也已有读取合并，不能把它们当成从未优化过的链路。行动台确认 Collection 保存后，还需刷新并确认新节点出现。这些是代码事实，不是各阶段实际耗时的测量结论。

R0 的两种模式：

|模式|行为|
|---|---|
|未采样|原流程；额外包装保持兼容，详细诊断关闭|
|A 原协作|保留原刷新方式，采集阶段|
|B 合并刷新|业务写入顺序与 A 相同；仅合并同一 PEO 实例收到的 EVA changed 与 SuperMemo Plan changed 通知刷新，运行中的新通知排到下一批|

手动刷新、跨视图跳转、restore、资格读取、保存及既有审计不经过 B 的合并队列。手动刷新仍可能和通知刷新并发。内核不缓存业务结果，不靠旧资格授权，不自动重试创建，不把等待超时当取消。冷启动承载接口尚未改为并行。

## 数据会怎样

本轮没有数据迁移。初始业务文件与基本版清洁压缩包逐字节一致。

|数据|继续由谁拥有|R0 处理|
|---|---|---|
|操作上下文声明、身份与 Kill 状态|Project Overview|沿用原契约|
|项目载体、材料、Tab|Workspace Mount|沿用原文件、ID、绑定|
|目标、周追踪、纵向计划、最终有效资格|Mandala|沿用原结构，项目域/目标域分开|
|启发性行动与 GTD 承载|GTD|沿用原 owner API|
|明确待办及创建回执|Collection Card|沿用幂等请求和写入确认|
|行动台 membership、草稿、显示状态|下一步行动台|沿用原存储与防丢路径|
|协调会话和性能摘要|实验内核|限量内存；显式复制；不写业务文件|

未来即使把这些模块装入一个插件，也可以先保持现有文件格式。若以后确实需要统一数据库，应单独设计旧 ID/别名映射、reader/writer 版本、附件与反向关系迁移、只读兼容、迁移前后对账和可回滚切换；不让新旧实现同时成为同一内容的写入主人。本轮没有实施此类迁移。

## 开始使用

1. 将“**大千-协作实验版**”作为另一个 Obsidian 库打开，允许本库社区插件。保留基本版以作对照。
2. 命令面板搜索“**打开协作实验**”，右侧打开实验控制台。原来的界面和操作入口仍可使用。
3. 选场景，点“**A · 原协作，采样60秒**”。随后只完成一项约定操作。先做一次空闲采样，可看到背景工作。
4. 核对刚创建/保存的对象身份和最新内容，尝试一次无破坏性的操作，例如展开刚创建的卡片。然后点击“**已核对新结果，且能继续操作**”。这个时刻含人工确认延迟，是可用时间的人工上界；函数返回不代替这一步。
5. 保留固定长度的后台观察窗口，再“**停止并查看摘要**”或“**复制本次诊断**”。采样到期会停止；仍在运行的已观测任务记为未结束，晚到结果单独计数。
6. 从相同初始副本/同等场景做 B，再按 B、A 顺序复测。修改数据的实验使用不同的等价初始副本，避免把第二次预热或已有对象复用误判成提速。

诊断不自动上传、不自动写盘、不包含正文、项目名或来源路径。复制后可贴回本聊天；另附冷/暖启动、打开的页面、数据量、Obsidian 版本和看到的结果。不需要自动重启你的实际大库。

## 三组场景

**新增项目/目标主键**：从原 Mandala 周追踪的“一键新增项目”或“一键新增九宫格主键目标”进入。观察主载体、PEO 声明、周追踪及三个承载的阶段结果。目标还要满足原有 EVA/GTD 承载条件。单个 Tab 创建成功不代表主键已满足全部有效资格。保留缺依赖/部分成功的结果，不重复创建来重试刷新。

**周追踪**：打开同一个有效项目或目标，填写一项测试记录，保存、重开并核对。诊断区分打开/读取、资格核查、保存返回。保存返回仍须用重开结果验收。归档行和当前有效行保持原有语义。

**下一步待办**：在行动台选定已有效且有精确 Collection 写入位置的主键，创建一个测试待办。分别观察 prepare、owner create、commit-confirmed、来源投影与行动台刷新。已确认写入但投影尚未完成时，不把创建失败/成功混为一谈。

如果初始示例还没有有效主键，先通过这些原生入口创建专用测试主键。没有预先伪造资格或自动创建正式待办来制造通过结果。

## 埋点与测量边界

已接入：Workspace 创建/承载；Mandala 项目/目标创建、三 owner 顺序阶段、双域资格、周追踪打开/读取/保存；GTD 承载入口；Collection 承载及待办 prepare/create；PEO 构建/Collection 投影/刷新；行动台 prepare/提交/资格/刷新。埋点清单与程序来源在实验目录的 `coordination-build-provenance.json`。

每次最多60秒；默认上限256条 span 与256条事件，owner 名称为会话内编号，丢弃量显式记录。不是全系统 trace：并行 span 只标“同一观察窗口”，不伪造父子因果；不能把重叠耗时相加当总时间。未埋点的监听器、任务、CPU/堆内存不可据此判定，摘要明确标 unknown/unavailable。队列全部闭环也不代表57个原插件整体空闲。

执行中的 hook 自报版本标记，内核加载时记录实际读取代码 SHA-256；磁盘清单另列。没有执行过的 hook 不算已验证加载。性能开关不关闭既有业务事务日志及审计。

## 当前证据与下一步

隔离测试覆盖实际补丁加载器、真实 carrier 协调方法、顺序和部分失败、批次合并、在途后的下一批、多实例、停止/卸载、溢出、诊断异常、保存回执和有界导出。合成 A/B 仅验证通知次数与批次数变化，不证明 Obsidian 整体提速，也不模拟大库笔记/图规模。

原生测试仍待你操作：正确性、保存重开、多 host、依赖缺失/慢响应、滚动及跳转、冷/暖会话、采样开关成本、重复开关后的后台与内存增长。小库可验证流程；能否改善大库须在后续匿名规模夹具或独立大库副本验证。测量前不宣称百分比收益。

观察到稳定收益后，再决定哪些模块值得真正合并，优先统一生命周期、数据读取和刷新调度；保留明确的数据所有权。若没有收益，关闭 B 或禁用实验内核即可恢复原调度，无需数据回迁。若将来手工移植回基本版，只能使用原 owner 导出/导入流程并备份，不能把整个旧库覆盖到新增内容上。

## 已知边界

实验中的 SuperMemo Concept 沿用基本版隔离方案：首次同机打开仅复制两棵树的结构。它不参与本轮性能内核，不代表其所有界面已在宿主验收。

这是一份本地实验交付。原来57个插件加1个实验内核，来源插件许可状况沿用基本版说明；没有对外发布或 GitHub 上传。
